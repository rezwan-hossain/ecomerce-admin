# Ecommerce Admin

An admin dashboard for an online store: orders, products, catalog and analytics. It started from the shadcn `dashboard-01`, `login-02` and `signup-02` blocks and was then customized.

**It is a UI demo.** All data is in-memory mock data and nothing is saved. Actions such as Save, Ship, Refund and Delete update React state and show a toast, but a refresh resets them. There is no auth and no backend yet.

## Stack

- **Next.js 16** (App Router, Turbopack). Its APIs differ from older versions, so read `node_modules/next/dist/docs/` before using a Next API (see AGENTS.md).
  - `params` is a Promise: `await params`.
  - Type pages and layouts with the global helpers `PageProps<"/route">` and `LayoutProps<"/route">`.
  - Run `npx next typegen` after adding or moving routes, or `tsc` reports stale route types.
- **React 19**, **TypeScript**, **Tailwind CSS v4**. There is no `tailwind.config`; the theme lives in `app/globals.css`.
- **shadcn/ui on Base UI** (`@base-ui/react`), not Radix:
  - Compose with the `render` prop, e.g. `<DropdownMenuTrigger render={<Button />}>`, not `asChild`.
  - A `Button` rendered as a link needs `nativeButton={false}`: `<Button nativeButton={false} render={<Link href="..." />}>`.
  - A `Select` needs an `items` prop (`{label, value}[]`), or the trigger shows the raw value instead of the label.
  - Collapsible panel state is exposed as the `data-panel-open` attribute.
- **Other libraries:** `@tanstack/react-table` v9 (only in `components/data-table.tsx`), `recharts` through `components/ui/chart.tsx`, `sonner` for toasts, `lucide-react` for icons, `zod`, `@dnd-kit`.
- `cn` comes from the `cn` npm package, re-exported by `lib/utils.ts`.
- Add shadcn components with `npx shadcn@latest add <name> --yes`.

## Structure

```
app/
├── layout.tsx            root: Inter font, TooltipProvider, Toaster
├── page.tsx              redirects to /dashboard
├── (admin)/              route group: sidebar + breadcrumb layout, not in the URL
│   ├── layout.tsx
│   ├── dashboard/        /dashboard
│   ├── orders/           /orders, /orders/{pending,returns,abandoned}, /orders/[id]
│   ├── shipping/         /shipping
│   └── products/         /products, /products/new, /products/[id]/edit,
│                         /products/{categories,brands,tags,options,variant-templates}
└── (auth)/               route group: split-screen layout, no sidebar
    ├── login/            /login
    └── signup/           /signup
```

- **New admin section** (e.g. Customers or Analytics): add `app/(admin)/<name>/page.tsx` and it inherits the sidebar and breadcrumb. Then add or update its entry in `navMain` in `components/app-sidebar.tsx`.
- **Sidebar menu:** `components/app-sidebar.tsx` holds the data. `components/nav-main.tsx` renders collapsible groups; an entry with `items` becomes an expandable sub-menu, and a sub-item can have a `badge`.
- **Breadcrumb:** `components/site-header.tsx` builds it from the URL. Add labels for new path segments to its `labels` map. Numeric IDs render as `#3204`, and slugs are title-cased.
- **Demo data:** everything is in `lib/demo-data.ts` (types, products, categories, brands, attributes, returns, abandoned carts, `currency`, `formatDate`). Orders come from `lib/data/orders.json`. Replace this module when a real backend arrives.
- **List pages** use the generic client component `components/list-table.tsx` (search, filter tabs, pagination). Pass it `columns` with `cell` functions. Functions can't cross the server-to-client boundary, so each list lives in its own client component (`components/orders/*`, `components/products/*`), and `page.tsx` stays a server component that passes data in.
- **Brands** (`/products/brands`) is the reference pattern for schema-aligned pages: the `Brand` type in `lib/demo-data.ts` mirrors the Prisma model (ISO date strings, `_count.products`), `lib/validations/brand.ts` holds the zod schema, and `components/brands/` holds the manager, the add/edit form (a side panel), and the delete confirmation. New records get IDs from `uuidv7()` in `lib/uuid.ts`. Follow this pattern when aligning other pages with the backend schema.
- **Categories** (`/products/categories`) is **connected to the real NestJS backend** (the other pages still use demo data).
  - `page.tsx` (server, `await connection()`) loads `GET /categories/tree` through `getCategoryTree()`.
  - `app/actions/category.actions.ts`: server actions return `{ success, data }` or `{ success: false, error, fieldErrors }`, and call `revalidatePath("/products/categories")`.
  - `lib/api.ts`: the fetch helper. It throws `ApiError` with `fieldErrors`.
  - `types/category.type.ts`: the API shapes. Tree nodes have `children?` and `_count.products`.
  - `components/categories/`:
    - `categories-manager.tsx` holds state (`useState`) and calls the actions, then `refresh()`es the tree.
    - `category-form.tsx` owns its own `useForm` + zod schema.
    - `category-tree.tsx` and `category-tree-row.tsx`: drop on a row = make it the last child; the drop zone = top level.
    - `category-dialogs.tsx`.
  - `lib/categories/tree-utils.ts`: `flattenTree`, `validateMove` (cycles, depth `MAX_DEPTH = 4`, inactive parent), `buildPath`, `slugify`.
  - Backend rules: `DELETE /:id` only works on an empty category (no children, no products). `/cascade` deletes the whole subtree. `/move` takes `{ newParentId, position }`.
- **Tags** (`/products/tags`) is also connected to the backend (`/tags` API). Files: `app/actions/tag.actions.ts`, `types/tag.type.ts`, `components/tags/tags-manager.tsx` (styled like Brands: stat cards, `ListTable` with tabs, search, sort and a row menu, and a delete dialog), and `components/tags/tag-form-sheet.tsx` (a side-panel add/edit form). Both action files share `handleRequest` / `ActionResponse` from `lib/action-response.ts`.
- **Options** (`/products/options`, replaces the old demo Attributes page) is connected to the backend (`/options` API). Files: `app/actions/option.actions.ts` (options and their values), `types/option.type.ts`, `components/options/options-manager.tsx` (Tags-style list), and `components/options/option-form-sheet.tsx`. A new option's name and values are created together. On an existing option, value changes save right away and the name saves with "Save name".
- **Variant Templates** (`/products/variant-templates`) is connected to the backend (`/variant-templates` API). Files: `app/actions/variant-template.actions.ts`, `types/variant-template.type.ts`, `components/variant-templates/variant-templates-manager.tsx` (list, shows how many variants each template makes), and `components/variant-templates/template-form-sheet.tsx` (pick options, then toggle their values). `page.tsx` also loads `getOptions()` for the form. A PATCH with `options` replaces all of them.
- **All Products** (`/products`) is connected to the backend. `getProducts()` in `app/actions/product.actions.ts` walks `GET /products` 100 at a time. `components/products/products-table.tsx` shows KPIs and the list. `page.tsx` also loads every variant's stock (`getStock()`), every order and every review (`getReviews()` in `review.actions.ts`) and sums them per product into a `ProductInsight` (variants' stock, units and revenue sold in the last 30 days, last sale, approved rating, pending reviews), so the table only gets numbers. KPIs: products, sellable units (and retail value), stock value at cost, needs restock, sold in 30 days, average rating. Rows show image, brand · primary category, SKU or variant count, status (and "Hidden"), sellable stock with a health dot and low/out/held counts, 30-day sales or "never sold"/"last …", rating, and price range. Tabs add Needs restock, No sales and Missing info (no image, brand or category; empty tabs are hidden); a product with nothing sellable shows "Out of stock" in red whatever its variants' own flags say, prices and revenue are whole taka, and KPI tiles use icons with lakh/crore short amounts; a sort menu (newest, name, best selling, lowest stock, highest rated, highest price) reorders rows before `ListTable` pages them. Row actions are Publish, Archive and Unarchive (`PATCH /products/:id/{publish,archive,unarchive}`; unarchive goes back to Draft) and Delete (a soft delete). Clicking the name (or "View details" in the row menu) opens the product page; Edit opens `/products/[id]/edit`. `types/product.type.ts` has the list row, detail and update shapes.
- **Orders** (`/orders` and `/orders/pending`) are connected to the backend. `getOrders()` in `app/actions/order.actions.ts` walks `GET /orders` 100 at a time; rows include `items`, `payments` and `shipments` (`types/order.type.ts`). `components/orders/orders-table.tsx` maps the 10 order statuses to labels and owns the shared `ORDER_STATUS_LABEL`, `PAYMENT_LABEL`, `CARRIER_LABEL` and `PROVIDER_LABEL` maps. Pending = PENDING, CONFIRMED, PROCESSING or READY_TO_SHIP. KPIs: in "all" mode orders (today, this week), paid revenue and average order, awaiting payment (unpaid and not cancelled), to fulfil (late after 2 days), shipped, cancelled with a percentage; in "pending" mode pending value, to confirm, packing, ready to ship, unpaid, oldest waiting. Rows show the order number with how long ago it was placed, customer (name with Guest/Account, phone with call and WhatsApp links, order count and delivery success rate across all their orders matched by phone or email, and the shipping address; the list has no addresses, so `getShippingAddresses()` reads each order's detail), items and units (with the first item's product picture from `getProducts()`, since order items have no images, and a "+N" badge for more items; clicking the picture opens `ItemsDialog`, which fetches each product with `getProduct()` to label the variant's options, e.g. Size: M, and shows the variant image, SKU, quantity × price and the order totals), fulfilment (latest parcel's courier, status and tracking number, else consignment id, linked to its tracking page when there is one, with a copy button; or "Not shipped" in amber after 2 days), status, and Amount (no separate Payment column: total, payment pill, provider, what's still due, and the discount). A ⋯ row menu offers View order, the next status (`NEXT`), Mark as paid (an open payment), Copy order number, Call / WhatsApp customer and Cancel order (`CancelDialog`, reason required); `NEXT`, `CANCELLABLE` and `CancelDialog` live in `orders-table.tsx` and the order page imports them. The table fits 1440px without sideways scroll. `RefreshButton` (exported from `orders-table.tsx`: `router.refresh()` in a transition) sits icon-only beside the sort menu and, labelled, in the order page header. Tabs: All, Unpaid, Unfulfilled, Shipped, Delivered, Cancelled (pending mode: To confirm, Packing, Ready to ship, Unpaid); a sort menu (newest, oldest, highest total). The order number links to the order page. Rows have checkboxes (`ListTable`'s optional `selected` / `onSelectedChange` / `bulkActions`: the header checkbox picks the page, "Select all N" the whole tab, and changing tab or search clears it); while any are selected the table header becomes a bulk bar with Next step (one item per `NEXT` step, only for orders it applies to, skipping `followsShipment`), Mark paid (open payments), Cancel (one reason for all, skipping `cancelBlockedBy`), Copy order numbers and Export CSV. `BulkDialog` in `orders-table.tsx` confirms, then runs the existing actions one order at a time (there's no bulk endpoint) and toasts the failures.
- **Order addresses** (`OrderAddress` in `types/order.type.ts`) are `fullName`, `phone`, one-line `fullAddress` (10–255), `thana` and `city` (the district), all required, plus optional `country` (orders from before thana have `thana: ""`); there are no first/last name, address lines, state or postcode any more (warehouses and suppliers still have those). `OrderAddressBody` is what the admin sends; `formatAddress()` shows "fullAddress · thana · city · country" skipping empty parts, and `pathaoAddress()` builds the one line Pathao gets (full address, then thana and city unless already in it), shown as "Pathao gets: …" in the Pathao popup. The edit form's order is District → Thana → Full address; it has no Country field (optional in the API, left as it is).
- **Order page** (`/orders/[id]`, `components/orders/order-detail.tsx`) loads `GET /orders/:id` (wrapped in `{ data }`; `OrderDetail` in `types/order.type.ts`), each item's product image (order items are snapshots without images), each variant's stock (`getVariantStock`), the order's ledger rows (`getReferenceMovements`, `/inventory/movements?referenceId=`) and the customer's other orders (all orders matched by email; the API can't filter by customer). It shows a progress stepper (or a cancelled banner with the reason), KPIs (total, paid, discount, cost of goods and margin from unit cost, customer orders, shipments), items with promotions plus available stock and the default pick rack per warehouse, totals with paid and balance due, shipments, stock movements, the status timeline (`statusLogs`), the customer with history, addresses (billing is hidden when it matches shipping), payments, refund requests and details. Actions in `order.actions.ts`: the next status on the happy path (`PATCH /orders/:id/status`, following the backend's `ORDER_STATUS_TRANSITIONS`; shipping commits reserved stock and cancelling releases it), Cancel with a required reason (`PATCH /:id/cancel`), Mark as paid or failed (`PATCH /:id/payments/:paymentId/{paid,failed}`), Add shipment (`POST /:id/shipments`: `carrier` is required and one of PATHAO, REDX, STEADFAST, CARRYBEE; blanks left out; COD amount defaults to the balance due), a per-shipment status select (`PATCH /:id/shipments/:shipmentId`; DELIVERED, CANCELLED and RETURNED are final), and refunds (`POST /:id/refund-requests` up to the paid amount not yet requested, then `PATCH /orders/refund-requests/:id/{approve,reject,process}`; processing marks the payment refunded and a full refund moves the order to REFUNDED). Items also show stock held for this order (the variant's `activeReservations` matched by order number), and Print uses `window.print()`, which prints only a small plain invoice: `components/orders/print-invoice.tsx` (store name, order number and date, customer and ship-to, item lines, totals, payment) portals itself into `<body>` as a `.print-sheet` that's hidden on screen, and a rule in `app/globals.css` hides everything else in `<body>` when printing (Ctrl+P too). Any page can reuse this by portalling its own `.print-sheet`. No `actedBy` is sent yet. Returns, Abandoned carts and the dashboard still use demo data; demo return rows no longer link to an order.
- **Returns from the courier** (set by the backend's Pathao webhook): order status `RETURNED` (whole parcel back; final, amber "Returned" badge, its own list tab) and payment `PARTIALLY_PAID` (COD partial delivery: `amount` is the cash collected, `metadata.orderedAmount` what was due; shown as "Partly paid ৳X of ৳Y", counted as paid, and nothing more is due). Order items have `returnedQuantity`. Receiving only some items turns an order into `PARTIALLY_RETURNED` ("Partly returned", amber outline badge with a tooltip, its own list tab); receiving the rest turns it into `RETURNED`. Returned units are left out of product sales. `getReturnState(order)` in `lib/orders/return-state.ts` is the one place that decides `none` / `returned` / `partial` and which items are still out. The order page shows an amber alert with "Receive returned items", which opens `ReceiveReturnsDialog` in `order-detail.tsx` (react-hook-form + zod; full quantities pre-filled for a returned parcel, 0 for a partial delivery; a Damaged tick sends units to the damage section). It calls `receiveReturnedItems` → `POST /orders/:id/returns` (can be repeated for later trips) and also revalidates `/inventory`. The backend takes one receipt per order at a time and refuses (400 "Only N × … can still be returned") one that asks for more than is still out, so the action refreshes on failure too, and the dialog follows the refreshed `returnedQuantity`: it clamps typed quantities to the new max and drops finished lines, closes with an "already received" toast when nothing is left, and shows a "Someone just received some of these items" strip on that 400. Lines with units back show "N returned", greyed when all are back.
- **Order numbers** are `ORD-100001`-style (one sequence) for new orders; older ones keep `ORD-20261104-113294` or `ORD-SEED-…`. Never parse or slice `orderNumber`; show it as it is. `ListTable` search trims and ignores case, so both formats match. Demo reservations use the new format.
- **Courier collected nothing:** a delivery where the courier was owed cash but collected ৳0 sets the COD payment `FAILED` with `failureMessage: "Courier collected nothing"`, `metadata.orderedAmount` and `metadata.collectedAmount: "0"`; the amount stays owed. `getReturnState()` treats it as a partial delivery (collected 0 plus anything paid since) on a DELIVERED / PARTIALLY_RETURNED order. The order page shows "৳0 of ৳X" under the payment and a destructive "Courier collected no cash" alert with **Record payment**, which opens `AddPaymentDialog` (also the Payments card's Add button): `recordPayment()` in `order.actions.ts` → `POST /orders/:id/payments` (provider/method from "Paid by"; at most what's owed), then `PATCH …/paid` with an optional transaction ID when "The money is already in" is ticked. The orders list shows a red "No cash collected" marker. Pathao's `shipment.metadata.pathaoReason` shows as "Pathao: …" on the shipment card.
- **The order follows its shipment** (backend): setting a parcel to shipped/in transit/out for delivery ships a READY_TO_SHIP order, DELIVERED and RETURNED also move it on (through SHIPPED), and a COD payment fails only when the whole order is returned. So on orders with a shipment (not cancelled), `followsShipment()` in `orders-table.tsx` hides Mark shipped / Mark delivered (header shows "Change the shipment status — the order follows it."; the row menu drops the step). Picking DELIVERED or RETURNED for a READY_TO_SHIP order's parcel asks first (`ConfirmShipmentDialog` and `needsShipmentConfirm` in `order-detail.tsx`, also used by the Shipping page). Finished parcels (`SHIPMENT_DONE`: delivered, cancelled, returned, failed) show a pill, not the select. Orders stuck on SHIPPED with a returned parcel (from before the fix) get a "Mark order returned" alert.
- **Change source (audit):** the backend records who made each change; the admin never sends it. `statusLogs[].source` + `courier`, `payment.metadata.settledBy` (+ `settledByCourier`, `settledAt`, `collectedAmount`, `orderedAmount`) and `shipment.metadata.lastChange` (`ChangeSource` in `types/order.type.ts`; missing on older payments and shipments). `SourceBadge` in `orders-table.tsx` shows Manual (amber, hand), the courier's name or "{courier} (sync)" (sky), Checkout or System (muted), with a tooltip. It's on each timeline row, next to the payment status ("Marked by hand — check against the courier's payout" on a manually settled COD payment), and under the shipment ("Delivered set by …"). The orders list shows a Manual marker under the amount when `settledByHand()` (COD settled by hand, or a delivered/returned parcel set by hand). While a COD payment is still pending, the shipment select (order page and Shipping page, via `shipmentStatusOptions()`) offers "Partly delivered", which asks for the cash collected (`PartialDeliveryDialog`) and sends DELIVERED with `collectedAmount`.
- **Cancelling after booking:** the backend refuses (409) to cancel an order while a parcel is live (pending, processing, shipped, in transit, out for delivery), and cancelling sets a pending COD payment to CANCELLED. `cancelBlockedBy()` in `orders-table.tsx` disables Cancel order (header and row menu) with "Cancel the {courier} parcel {id} first". Live parcels get "Parcel cancelled at courier" on the order page: a Pathao parcel is synced first; if it isn't cancelled yet (or for other couriers), a confirm marks it CANCELLED by hand. A cancelled payment shows a grey pill. The same live-parcel rule (`liveShipment()` in `orders-table.tsx`, which `cancelBlockedBy()` also uses) locks the **shipping address**: the backend answers 409 because Pathao keeps the address it got at booking. The order page's Addresses card has Edit buttons (`AddressDialog` in `order-detail.tsx`, only changed fields sent, until the order ships): Ship to is disabled with "Booked with {courier} ({id}). Cancel the parcel first, then change the address and book again.", Bill to stays editable. A refused save shows a toast and keeps the dialog open. After the shipping address changes on an order with a cancelled parcel, the card offers "Address changed. Book with Pathao again?", which opens `PathaoDialog`; that dialog's inline address Edit is blocked the same way.
- **Pathao courier** (the backend's `/courier/pathao` API, `docs/api/pathao-courier.md`): `app/actions/pathao.actions.ts`, `types/pathao.type.ts`. Responses are Pathao's snake_case shapes with no `{ data }` wrapper. On the order page, "Book with Pathao" (next to Add shipment, while the order can ship and has no Pathao parcel still on the way) books right away with the usual settings (normal delivery, parcel, 0.5 kg; the backend fills in the item count and the cash still due) and shows the outcome as a `PathaoLog` card at the top of the Shipments card. The pencil beside it opens `PathaoDialog` in `order-detail.tsx` for custom settings: the recipient, with an Edit button that edits the shipping address inline (`updateOrderAddress` → `PATCH /orders/:id/addresses/SHIPPING` with only the changed fields, allowed until the order ships) and amber warnings from `pathaoProblems()` mirroring the backend's recipient checks (BD mobile, name ≥ 3, thana present, the Pathao line ≥ 10), the recipient as Pathao gets it, pickup store (blank = `PATHAO_STORE_ID`; stores are added in the Pathao merchant panel, the API only lists them), delivery and item type, weight 0.5–10 kg, item count, whole-taka cash to collect (defaults to the balance due), contents and a rider note. The backend has no city/zone/area or price endpoints (Pathao reads the address), so the delivery charge is "Shown after booking". Booking saves a PATHAO shipment (consignment id as tracking number; Pathao's fee and last status in `shipment.metadata`). Pathao shipments that aren't finished get a Sync button (`POST /shipments/:id/sync`), and show Pathao's last status. Pathao's errors come back as 502 with Pathao's message. Booking and Sync also return the raw `reply` (or raw error body, via `withReply` in `pathao.actions.ts`): the dialog keeps it open in an "API reply" box (Done closes it after a booking), and Sync shows it in its toast. **Bulk booking:** the orders list's bulk bar has "Send with Pathao" for the selected orders that `canBookPathao()` accepts (`orders-table.tsx`, also used by the order page: CONFIRMED/PROCESSING/READY_TO_SHIP and no open Pathao parcel, `hasOpenPathao()`); the rest are counted as "can't be sent". `components/courier/pathao-bulk-dialog.tsx` holds `PathaoMark`, the shared option fields (`PathaoOptions`, `PATHAO_DEFAULTS`, `pathaoOptionsSchema`, `pathaoOptionsBody`; the single `PathaoDialog` adds item count and cash via `extra`) and `PathaoBulkDialog`: options once, a read-only table of the orders (amber when there's no address or phone), then `bulkBookPathaoShipments` (`POST /courier/pathao/shipments/bulk`, raw `{ booked, failed, skipped }`) 10 ids at a time, one request after another, with a progress bar and Stop. Any `skipped` or a failed request stops the run and lists the rest as Not tried ("Send these again" reopens the form with them and the same options); failed 504s warn to check the Pathao panel first, and "Send failed again" only offers failures that aren't 504/404/409.
- **Shipping** (`/shipping`, the sidebar's Store › Shipping) is built from the orders API; the backend has no shipping zones or rates, only shipments on orders. `page.tsx` loads every order (`getOrders()`, whose rows include full shipments) and fetches the detail of orders waiting to ship for their destination city (the list has no addresses). `components/shipping/shipping-board.tsx` shows KPIs (to pack, ready to hand over, on the road, delivered in 30 days with average days, cash to collect on delivery, failed or returned), a parcel pipeline (booked → picked up → in transit → out for delivery → delivered, plus failed or returned), "Needs attention" (ready orders with no parcel, orders waiting over 2 days to pack, parcels not picked up after a day, parcels on the road over 3 days, failed or returned parcels; each links to its order), cash on delivery (to collect, held by couriers = delivered but the order's payment isn't marked paid, settled), 30-day shipping costs (order `shippingAmount` charged to customers against shipment `shippingAmount` paid to couriers), one card per courier (Pathao, RedX, Steadfast, CarryBee: parcels, delivery rate, on the road, delivered, cash to collect, average delivery time), the fulfilment queue (CONFIRMED, PROCESSING and READY_TO_SHIP orders, oldest first, with destination, COD or paid, parcel and wait time) and every shipment with an inline status select (`updateShipmentStatus`). Parcels are booked from the order page's Add shipment. A failed or returned parcel is only an open problem (`openProblem` in `shipping-board.tsx`: KPI, "Needs attention", the "Needs follow-up" tab) until another parcel goes out, the order closes, or every returned item is back; the pipeline tile shows the all-time count with "N open". The courier's fee is `courierFee()` in `order-detail.tsx`: Pathao's `metadata.pathaoDeliveryFee` when present, since the shipment's `shippingAmount` can just copy the customer's delivery charge. Courier logos are `public/couriers/{pathao,redx,steadfast,carrybee}.png` (200px, from each courier's own site); `CourierLogo` in `orders-table.tsx` shows them (Pathao's is cropped round) in the orders list, items popup, source badges, the order page's shipments, the Shipping page and the sales report's couriers. `Shipment` in `types/order.type.ts` is shared by the list and detail types; the courier labels and shipment status helpers are exported from `order-detail.tsx`.
- **Inventory** follows the user's "Haat operations" HTML mockup. The sidebar's Store section links to it, and `app/(admin)/inventory/layout.tsx` adds a grouped section nav (`components/inventory/inventory-nav.tsx`: Stock, Operations, Planning).
  - **Live (the backend's `/inventory` API):**
    - Overview `/inventory` (`inventory-overview.tsx`, a server component): summary KPIs, recent movements, low/out-of-stock list, ledger balance checks, and per-warehouse totals.
    - Products `/inventory/products` (`product-shelf.tsx` + `product-stock-sheet.tsx`), from the user's "Stockroom Light" example: a card per product (from `getProducts()` joined with `getStock()` by product id) showing each variant's sellable stock; a toggle switches between a list (`ProductList`, one table row per product, the default) and the cards; both page 12 products at a time. A card opens a drawer with brand, category and tag chips, three actions (Edit product, Add stock, Order from supplier, which links to Purchase orders), stats, a variant × warehouse grid and recent movements (`getProductMovements` fetches per variant and merges, since the ledger only filters by variant). A grid cell opens `stock-history-sheet.tsx` for that variant. "Add stock" posts many variants × warehouses at once to `POST /inventory/adjustments/bulk` (`bulkAdjustStock`, all or nothing). "New product" and "Edit product" link to the existing product pages.

  - **Suppliers** `/inventory/setup/suppliers` is live (`/suppliers` API): `app/actions/supplier.actions.ts`, `types/supplier.type.ts`, and `Suppliers` + `SupplierSheet` in `setup.tsx`. There's no backend for groups, so they're saved in `localStorage` (`customer-groups`), with six starter groups until the first change. `components/customers/group-sheet.tsx` holds the `Group`/`Rule` types, `matches()`, `ruleText()` and the add/edit panel (live match count); `customer-groups.tsx` shows a card per group (rules, members, share, paid, avatars; Edit, Duplicate, Delete) and the picked group's members with Copy phones (one per line, for SMS tools) and Export CSV.
- **Add customer** (`/customers/new`, `components/customers/customer-form.tsx`): react-hook-form + zod form for a customer account matching the backend's `User` model (first name, optional last name, email, BD mobile, birthday, gender, photo link, active), with a live preview card and an amber warning when the phone or email already belongs to someone who ordered (matched with `customerKey()` against `getOrders()`). It calls `createCustomer()` in `app/actions/customer.actions.ts` → `POST /users` (`types/customer.type.ts`), which **the backend doesn't have yet** (the users controller is empty): a 404 shows "Adding customers isn't available yet". The breadcrumb reads "New customer" under Customers.
- **Shared UI:** `page-header.tsx`, `stat-cards.tsx`, `status-badge.tsx` (maps order, product and return statuses to icons).
- The dashboard's big orders table (`components/data-table.tsx`) is the original shadcn block adapted to orders: drag to reorder, and a detail drawer.

## Design conventions

- **Brand color is blue** (`--primary: #256abf` light, `#3987e5` dark), set in `app/globals.css`. The sidebar and page background are a cool gray.
- **Auth pages use black buttons.** `app/(auth)/layout.tsx` overrides `--primary` to `--foreground` for the form area only. Keep that scoped.
- **Charts** use the validated categorical palette in `--chart-1` … `--chart-5` (blue, orange, aqua, yellow, magenta). Assign them in that order and don't cycle.
  - Two series: `chart-1` and `chart-2`.
  - Lines 2px, area fill about 10% opacity, bars at most 24px thick with 4px rounded ends.
  - Two or more series always get a legend.
  - Text is never colored with the series color.
- Status colors (green or red trend badges) always come with an icon and a label.
- Dark mode works through the `.dark` class. There is no theme toggle yet.
